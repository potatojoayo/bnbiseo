# 수리 요청 기능 최종 기획

## 1. 목표

호스트가 숙소의 고장, 이상 증상, 수리가 필요한 상황을 앱에서 간단히 접수하고, 이후 매니저가 유선 협의, 견적 발송, 방문, 완료 보고까지 이어서 처리할 수 있는 수리 요청 기능을 만든다.

이 기능의 핵심 원칙은 다음과 같다.

- 호스트가 정확한 원인이나 시설물을 몰라도 요청할 수 있어야 한다.
- 시설물을 알고 있으면 선택할 수 있어, 매니저가 부품을 미리 준비해 방문할 수 있다.
- 초기 요청 입력은 최대한 가볍게 만든다.
- 일정과 견적은 매니저가 호스트와 유선 협의한 뒤 시스템에 입력한다.
- 매니저가 견적을 발송해도 결제 전까지는 최종 확정이 아니다.
- 완료 시 보고서(사진 + 조치내용)를 반드시 작성해 호스트가 결과를 확인할 수 있도록 한다.

---

## 2. 사용자 역할

### 호스트

- 수리 요청 생성
- 희망 일정 입력
- 상세 증상 설명 입력
- 관련 시설물 선택 (선택, 다중 선택 가능)
- 사진 첨부 (선택)
- 매니저와 유선 일정 협의
- 제안된 방문 일정과 견적서 확인
- 결제
- 진행 상태 및 완료 보고서 확인

### 매니저

- 신규 수리 요청 확인
- 호스트와 유선 연락해 일정/견적 협의
- 확정 일정 + 견적서 시스템 입력/발송
- 당일 방문 후 작업 시작 처리
- 작업 완료 후 보고서 작성 (사진 + 조치내용)

---

## 3. 호스트 요청 생성

### 입력 항목

- 숙소 선택 (필수)
- 상세 설명 (필수)
- 관련 시설물 선택 (선택, 다중 선택 가능)
- 사진 첨부 (선택, 0장 이상)
- 희망 날짜/시간 1개 (필수)

### 입력 원칙

- 공간 선택 없음
- 시설물 직접 입력(커스텀 추가) 없음 — 자산 DB 오염 방지
- 정확한 시설물을 몰라도 상세 설명만으로 요청 가능
- 시설물을 알고 있으면 선택해 매니저가 부품을 미리 준비할 수 있도록 도움
- 원격 요청도 가능해야 하므로 사진은 필수가 아님

### 시설물 선택 UX

- 선택한 숙소의 자산 DB에서 **썸네일 + 이름 + 위치** 기반 리스트 노출
- 다중 선택 허용
- 명시적 "잘 모르겠어요 / 건너뛰기" 옵션 제공
- 자산 DB에 없으면 선택하지 않고 건너뛰고, 매니저가 현장 확인 후 자산 DB에 등록

### 예시 요청

- 집 전체 바닥에 물이 찼어요.
- 세탁기인지 배수 문제인지 모르겠는데 물이 새요.
- 문이 잘 안 닫히고 열 때 소리가 나요.
- 거실 에어컨에서 찬 바람이 안 나와요. (시설물: 거실 에어컨 선택됨 → 매니저가 필터/가스 준비 가능)

### 추천 UX 문구

- 상세 설명: 증상과 현재 상황을 자유롭게 적어주세요.
- 시설물 선택: 문제가 있는 시설물을 알고 계신가요? 선택해주시면 매니저가 필요한 부품을 미리 준비할 수 있어요. 모르시면 건너뛰셔도 괜찮습니다.
- 사진: 사진이 있으면 첨부해주세요. 없어도 요청할 수 있습니다.
- 희망 일정: 희망 방문 일시를 선택해주세요. 매니저가 유선으로 최종 일정을 조율합니다.

## 4. 전체 플로우

1. 호스트가 수리 요청을 생성한다.
2. 요청 상태는 `submitted`가 된다.
3. 매니저에게 신규 수리 요청 알림이 발송된다.
4. 매니저가 호스트에게 유선 연락해 일정과 견적을 협의한다.
5. 매니저가 확정 일정과 견적서를 시스템에 입력해 발송한다.
6. 요청 상태는 `quoted`가 된다.
7. 호스트가 상세 화면에서 제안 일정과 견적을 확인한다.
8. 호스트가 결제를 진행한다.
9. 요청 상태는 `confirmed`가 된다.
10. 당일 매니저가 현장에서 `작업 시작` 버튼을 누른다.
11. 요청 상태는 `in_progress`가 된다.
12. 수리 완료 후 매니저가 조치 보고서(사진 + 조치내용)를 작성한다.
13. 요청 상태는 `completed`가 된다.

---

## 5. 상태값 정의

### `submitted`

- 호스트가 요청을 접수한 상태
- 매니저 유선 협의 대기

### `quoted`

- 매니저가 확정 일정 + 견적서를 입력해 발송한 상태
- 호스트가 일정/견적을 확인하고 결제 대기
- 아직 결제 전이므로 최종 확정 상태는 아님

### `confirmed`

- 호스트가 결제를 완료한 상태
- 방문 일정 최종 확정

### `in_progress`

- 매니저가 현장에서 작업 시작 버튼을 눌러 작업 진행 중

### `completed`

- 매니저가 조치 보고서 작성을 완료한 상태
- 호스트가 완료 사진과 조치내용을 확인 가능

### `cancelled`

- 요청 취소

## 6. 일정 개념 정리

수리 요청에는 두 가지 일정 값이 있다.

### 희망 일정

- 호스트가 요청 생성 시 입력하는 값
- 필드 예시: `preferred_schedule_at`
- 참고용 일정
- 이 값만으로는 방문이 확정되지 않음

### 확정 방문 일정

- 매니저가 호스트와 유선 협의 후 입력하는 값
- 필드 예시: `scheduled_at`
- `quoted` 상태에서 호스트에게 노출
- 결제 완료 전까지는 최종 확정 아님

### 최종 확정 시점

- 호스트가 결제를 완료하면 방문 일정이 최종 확정된다
- 즉, 진짜 확정 상태는 `confirmed`부터다

## 7. 알림 규칙

### 호스트 요청 접수 시

- 매니저에게 신규 수리 요청 알림 발송

### 매니저가 일정/견적 발송 시

- 호스트에게 알림 발송
- 알림 문구:
  - 수리 방문 일정과 견적이 도착했습니다. 확인 후 결제를 진행해주세요.

### 호스트 결제 완료 시

- 호스트에게 최종 확정 안내
- 매니저에게 확정 알림 발송
- 알림 문구:
  - 수리 방문 일정이 확정되었습니다.

### 작업 시작 시

- 호스트에게 작업 시작 알림 발송

### 작업 완료 시

- 호스트에게 완료 알림 + 조치 보고서 확인 안내

## 8. 화면 구성

### 호스트 화면

- 수리 요청 생성 페이지
- 수리 요청 목록 페이지
- 수리 요청 상세 페이지 (진행 상태별 다른 정보 노출)

- 완료 보고서 확인 화면

### 매니저 화면

- 수리 요청 목록 페이지
- 요청 상세 페이지
- 일정 + 견적서 입력 기능
- 작업 시작 버튼
- 조치 보고서 작성 기능

### 호스트가 보는 정보

### 매니저가 보는 정보

- 요청 상태
- 숙소 정보 및 호스트 연락처
- 희망 일정
- 상세 설명
- 선택된 시설물 상세 (이름, 브랜드, 모델넘버, 구매처, 위치) — 부품 준비에 활용
- 요청 사진
- 견적 금액
- 방문 일정
- 작성한 조치 보고서

## 10. 완료 조치 보고서

### 필수 항목

- 조치 사진: 최소 1장
- 조치내용 텍스트: 필수

### 선택 항목

- 추가 메모

### 작성 시점

- `in_progress` 상태에서 매니저가 작업 완료 후 작성
- 보고서 제출 완료 시 상태는 `completed`로 전환

### 노출 대상

- 호스트 상세 화면에서 항상 확인 가능
- 매니저 상세 화면에서도 조회 가능

- `additional_notes` (선택)

- `completion_report_id`

## 12. 운영상 중요한 규칙

### 1. 결제 전까지는 완전 확정이 아니다

- 매니저가 일정/견적을 발송해도 상태는 `quoted`
- 호스트가 결제해야 `confirmed`

### 2. 매니저 일정은 결제 전 임시 홀드 개념이다

- 결제 전에는 일정 변경 가능성이 있음
- 운영상 완전 락으로 보지 않는다

### 3. 초기 입력은 가볍게 유지한다

- 사진 미첨부 허용
- 시설물 선택은 선택 사항 (다중 선택 가능, "잘 모르겠어요" 허용)
- 공간 선택 없음
- 시설물 커스텀 입력 없음

### 4. 호스트가 정확히 진단하지 못해도 된다

- 문제의 정확한 원인 파악은 매니저 유선 협의 단계에서 처리

### 5. 완료 보고서는 필수다

- 사진 최소 1장 + 조치내용 없이는 `completed` 전환 불가
- 호스트 신뢰 확보와 사후 분쟁 방지 목적

## 13. MVP 범위

첫 버전에서는 아래까지만 구현하면 충분하다.

- 호스트 수리 요청 생성
- 매니저의 신규 요청 조회
- 매니저의 일정 + 견적서 입력/발송
- 호스트의 일정/견적 확인 및 결제
- 매니저의 작업 시작 처리
- 매니저의 조치 보고서 작성 (사진 + 조치내용 필수)
- 상태별 목록/상세 화면

처음부터 넣지 않아도 되는 것:

- 관리자 역할 분리
- 자동 매니저 매칭
- AI 견적
- 매니저 일정 캘린더 연동
- 시설물 커스텀 입력
- 견적 거부 후 재협의 플로우 (MVP에서는 취소 → 재요청)
- 추가 작업 발생 시 비용 조정 (실제 비용 vs 견적 비용 분리)

## 14. 한 줄 요약

호스트는 숙소, 희망 일정, 상세 설명 중심으로 가볍게 수리 요청을 만들고(아는 경우 시설물을 선택해 매니저의 부품 준비를 돕는다), 매니저가 유선 협의 후 확정 일정과 견적서를 발송한다. 호스트가 결제하면 방문이 최종 확정되고, 매니저가 현장에서 작업을 시작한 뒤 완료 시 사진과 조치내용이 담긴 조치 보고서를 작성해 호스트에게 공유한다.
