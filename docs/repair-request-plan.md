# 수리 요청 기능 최종 기획

## 1. 목표

호스트가 숙소의 고장, 이상 증상, 수리가 필요한 상황을 앱에서 간단히 접수하고, 이후 관리자와 매니저가 견적, 배정, 일정 조율, 방문, 완료까지 이어서 처리할 수 있는 수리 요청 기능을 만든다.

이 기능의 핵심 원칙은 다음과 같다.

- 호스트가 정확한 원인이나 시설물을 몰라도 요청할 수 있어야 한다.
- 초기 요청 입력은 최대한 가볍게 만든다.
- 견적 확정 전에는 관리자만 요청을 볼 수 있다.
- 일정은 배정된 매니저가 호스트와 협의한 뒤 시스템에 입력한다.
- 매니저가 일정을 입력해도 결제 전까지는 최종 확정이 아니다.

---

## 2. 사용자 역할

### 호스트

- 수리 요청 생성
- 희망 일정 입력
- 상세 증상 설명 입력
- 시설물 선택 가능
- 사진 첨부 가능
- 매니저와 일정 협의
- 제안된 방문 일정 확인
- 결제
- 진행 상태 및 완료 내역 확인

### 관리자

- 최초 요청 확인
- 견적 확정
- 매니저에게 요청 공개
- 매니저 배정
- 전체 상태 관리

### 매니저

- 견적 완료 후 공개된 요청 확인
- 배정된 요청 수행
- 호스트와 방문 일정 협의
- 협의된 방문 일정 입력
- 작업 시작 및 완료 처리

---

## 3. 호스트 요청 생성

### 입력 항목

- 숙소 선택
- 희망 일정 1개
- 시설물 선택
  - 다중 선택 가능
  - 선택 안 해도 됨
- 상세 설명
- 사진 첨부
  - 선택
  - 0장 가능

### 입력 원칙

- 공간 선택 없음
- 직접 입력용 시설물명 없음
- 시설물 선택은 보조 정보
- 정확한 시설물을 몰라도 상세 설명만으로 요청 가능
- 원격 요청도 가능해야 하므로 사진은 필수가 아님

### 예시 요청

- 집 전체 바닥에 물이 찼어요.
- 세탁기인지 배수 문제인지 모르겠는데 물이 새요.
- 문이 잘 안 닫히고 열 때 소리가 나요.

### 추천 UX 문구

- 시설물 선택: 관련 시설물이 있다면 선택해주세요. 정확하지 않아도 괜찮습니다.
- 상세 설명: 증상과 현재 상황을 자유롭게 적어주세요.
- 사진: 사진이 있으면 첨부해주세요. 없어도 요청할 수 있습니다.
- 희망 일정: 희망 방문 일시를 선택해주세요. 배정된 매니저와 최종 일정을 조율합니다.

---

## 4. 전체 플로우

1. 호스트가 수리 요청을 생성한다.
2. 요청 상태는 `submitted`가 된다.
3. 관리자에게만 알림이 가고, 관리자만 요청을 볼 수 있다.
4. 관리자가 요청을 검토하고 견적을 확정한다.
5. 요청 상태는 `estimated`가 된다.
6. 이 시점부터 매니저에게 요청이 공개된다.
7. 관리자가 매니저를 배정한다.
8. 요청 상태는 `assigned`가 된다.
9. 배정된 매니저가 호스트와 방문 일시를 협의한다.
10. 매니저가 협의된 방문 일시를 시스템에 입력한다.
11. 요청 상태는 `schedule_proposed`가 된다.
12. 호스트에게 방문 일정 제안 알림이 발송된다.
13. 호스트가 상세 화면에서 제안 일정과 견적을 확인한다.
14. 호스트가 결제를 진행한다.
15. 요청 상태는 `confirmed`가 된다.
16. 작업 시작 시 `in_progress`가 된다.
17. 작업 완료 시 `completed`가 된다.

---

## 5. 상태값 정의

### `submitted`

- 호스트가 요청을 접수한 상태
- 관리자만 조회 가능
- 아직 견적 미확정

### `estimated`

- 관리자가 견적을 확정한 상태
- 매니저에게 공개 가능
- 아직 매니저 미배정

### `assigned`

- 관리자가 매니저를 배정한 상태
- 배정된 매니저가 호스트와 일정 협의 중

### `schedule_proposed`

- 매니저가 호스트와 협의한 방문 일시를 입력한 상태
- 호스트가 제안 일정과 견적을 확인할 수 있음
- 아직 결제 전이므로 최종 확정 상태는 아님

### `confirmed`

- 호스트가 결제를 완료한 상태
- 방문 일정 최종 확정

### `in_progress`

- 실제 수리 작업 진행 중

### `completed`

- 수리 작업 완료
- 완료 사진, 작업 메모, 실제 비용 등 확인 가능

### `cancelled`

- 요청 취소

## 6. 일정 개념 정리

수리 요청에는 두 가지 일정 값이 있다.

### 희망 일정

- 호스트가 요청 생성 시 입력하는 값
- 필드 예시: `preferred_schedule_at`
- 참고용 일정
- 이 값만으로는 방문이 확정되지 않음

### 제안 방문 일정

- 배정된 매니저가 호스트와 협의 후 입력하는 값
- 필드 예시: `scheduled_at`
- `schedule_proposed` 상태에서 호스트에게 노출
- 결제 완료 전까지는 최종 확정 아님

### 최종 확정 시점

- 호스트가 결제를 완료하면 방문 일정이 최종 확정된다
- 즉, 진짜 확정 상태는 `confirmed`부터다

## 7. 알림 규칙

### 호스트 요청 접수 시

- 관리자에게만 알림 발송

### 관리자 견적 확정 시

- 매니저에게 새 수리 요청 알림 발송

### 관리자 매니저 배정 시

- 해당 매니저에게 배정 알림 발송

### 매니저가 방문 일정 입력 시

- 호스트에게 알림 발송
- 알림 문구:
  - 수리 방문 일정이 제안되었습니다. 확인 후 결제를 진행해주세요.

### 호스트 결제 완료 시

- 호스트에게 최종 확정 안내
- 관리자와 매니저에게 확정 알림 발송
- 알림 문구:
  - 수리 방문 일정이 확정되었습니다.

### 작업 완료 시

- 호스트에게 완료 알림 발송

## 11. 운영상 중요한 규칙

### 1. 결제 전까지는 완전 확정이 아니다

- 매니저가 방문 일시를 입력해도 상태는 `schedule_proposed`
- 호스트가 결제해야 `confirmed`

### 2. 매니저 일정은 결제 전 임시 홀드 개념이다

- 결제 전에는 일정 변경 가능성이 있음
- 운영상 완전 락으로 보지 않는다

### 3. 초기 입력은 가볍게 유지한다

- 시설물 미선택 허용
- 사진 미첨부 허용
- 공간 선택 없음

### 4. 호스트가 정확히 진단하지 못해도 된다

- 문제의 정확한 원인 파악은 관리자/매니저 단계에서 처리

## 12. MVP 범위

첫 버전에서는 아래까지만 구현하면 충분하다.

- 호스트 수리 요청 생성
- 관리자 전용 초기 검토
- 관리자 견적 확정
- 매니저 공개 및 배정
- 매니저의 방문 일정 입력
- 호스트의 일정 확인 및 결제
- 작업 시작 및 완료 처리
- 상태별 목록/상세 화면

처음부터 넣지 않아도 되는 것:

- 자동 매니저 매칭
- AI 견적
- 매니저 일정 캘린더 연동
- 내부 분류 태그 자동화
- 부품 자동 추천

---

## 13. 한 줄 요약

호스트는 숙소, 희망 일정, 상세 설명 중심으로 가볍게 수리 요청을 만들고, 관리자가 먼저 견적을 확정한 뒤 매니저를 배정한다. 배정된 매니저가 호스트와 협의한 방문 일시를 시스템에 입력하면 호스트는 제안된 일정을 확인하고 결제하며, 결제 완료 후 방문 일정이 최종 확정된다.
